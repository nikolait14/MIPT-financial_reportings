# Backend API, режимы хранения и доказательства

## Статус документа

Backend API реализован. Этот документ одновременно задает публичный контракт и
описывает фактическое поведение версии `1.0`.

По разъяснению организаторов дополнительные требования к хранению не вводятся:
необходимо соблюдать ограничение самого кейса и не передавать конфиденциальные данные
во внешние API. Текущий pipeline локален и внешние OCR/LLM API не использует.

Продуктовым целевым режимом следующей итерации выбран `PERSISTENT`. `EPHEMERAL`
сохраняется как поддерживаемая политика deployment для заказчиков, запрещающих
постоянное хранение. Выбор режима не меняет финансовую схему результата.

Реализация находится в `src/financial_verification/backend`, Docker-сервис называется
`api`, а интерактивная OpenAPI-документация доступна по `/docs`.

## Цель этапа

Создать backend, который:

- принимает комплект КФЗ и подтверждающих документов без перезагрузки будущего UI;
- запускает существующий локальный pipeline;
- сообщает прогресс обработки;
- возвращает единый структурированный результат сверки;
- выделяет OCR-неуверенности и содержательные расхождения;
- связывает каждый вывод с фрагментом исходного документа;
- не изменяет оригинальные документы;
- не использует внешние OCR или LLM API;
- работает как без постоянного хранения, так и с ним без изменения публичного API.

Информативное плоское представление результата зафиксировано в документе
[Прототип информативного отчета](informative-report-prototype.md). Детальный режим
должен показывать те же данные интерактивно: расхождение → расчет → документы →
подсвеченный фрагмент.

## Принципы

1. У backend один публичный контракт для всех режимов хранения.
2. Способ хранения выбирается политикой deployment, а не произвольным параметром
   запроса пользователя.
3. Финансовая логика не дублируется в API: CLI, Docker pipeline и API используют один
   application layer.
4. Расчеты выполняются детерминированно через `Decimal`.
5. Оригинальные документы неизменяемы; подсветка является визуальным overlay.
6. OCR-неуверенность не считается финансовым расхождением.
7. Недостаток данных не подменяется нулем и не превращается в финансовую ошибку.
8. Markdown, будущий HTML, PDF и API строятся из одного `VerificationResult`.
9. Документы не передаются сторонним сервисам и не используются для обучения.

## Два режима одного API

```text
                         единый FastAPI
                              │
                 конфигурационная StoragePolicy
                              │
              ┌───────────────┴────────────────┐
              │                                │
          EPHEMERAL                        PERSISTENT
      временная обработка             сохраняемые проверки
      без постоянного архива          и повторное открытие
```

### EPHEMERAL

Используется, если хранение запрещено или еще не согласовано.

- исходные документы находятся в изолированном временном workspace;
- после завершения pipeline документы и полноразмерные страницы удаляются;
- готовый `VerificationResult` временно хранится в RAM;
- результат доступен до истечения TTL;
- детальный просмотр использует локальные `File`-объекты браузера;
- повторный запуск после очистки требует повторной загрузки;
- перезапуск backend удаляет активные задания и несохраненные результаты.

Полностью обработать файл без попадания байтов в память или временный каталог
невозможно. Под отсутствием хранения понимается отсутствие постоянной записи в БД,
постоянный volume или архив.

### PERSISTENT

Выбран целевым продуктовым режимом текущего этапа. Существующая файловая реализация —
технический baseline, который развивается в историю версий документов и запусков.

- документы и результаты сохраняются в управляемом хранилище;
- старую проверку можно открыть повторно;
- доступны история и повторный запуск;
- сравнение версий и восстановление являются задачей следующей реализации;
- backend может отдавать документ и доказательные изображения;
- срок хранения задается политикой;
- удаление доступно через API; аудит действий относится к production-hardening.

Локальная демонстрация может использовать PERSISTENT без внешних сервисов. Публичный
production-режим потребует авторизации, изоляции пользователей, шифрования, retention
и аудита доступа.

## Матрица возможностей

| Возможность | EPHEMERAL | PERSISTENT |
|---|---:|---:|
| Загрузка и проверка | Да | Да |
| Прогресс без обновления страницы | Да | Да |
| Получение структурированного результата | До TTL | До удаления или retention |
| Просмотр документа | Из локального файла браузера | Из браузера или backend |
| История проверок | Только активные сессии | Да |
| Повторный запуск без загрузки | Нет | Да |
| Восстановление после рестарта | Нет | Да |
| Сравнение версий | Нет | Следующая итерация |
| Экспорт MD/JSON | Да | Да |
| Экспорт PDF/XLSX | Следующий этап | Следующий этап |
| Ручное удаление | Очистка сессии | Удаление сохраненных данных |

## Поток обработки

```text
POST /api/v1/verifications
        ↓
валидация количества, форматов и размера файлов
        ↓
изолированный workspace run-{uuid}
        ↓
OCR PDF/PNG + нативный DOCX/XLSX
        ↓
реестр документов
        ↓
дубли / договор / период / технические ошибки
        ↓
классификация и Decimal-агрегирование
        ↓
сверка КФЗ
        ↓
EvidenceReference + Annotation + Finding
        ↓
VerificationResult
        ↓
ответ пользователю
        ↓
очистка согласно StoragePolicy
```

## Публичный API

### Системные endpoints

```text
GET /health/live
GET /health/ready
GET /api/v1/capabilities
```

```json
    "results_persisted": false,
    "result_ttl_seconds": 1800,
    "history_available": false,
    "rerun_without_upload": false
  },
  "limits": {
    "max_files": 100,
    "max_file_size_bytes": 52428800,
    "max_total_size_bytes": 262144000,
    "pipeline_stage_timeout_seconds": 600
  }
}
```

### Полная проверка

```text
POST   /api/v1/verifications
GET    /api/v1/verifications/{id}
GET    /api/v1/verifications/{id}/events
GET    /api/v1/verifications/{id}/result
GET    /api/v1/verifications/{id}/documents
GET    /api/v1/verifications/{id}/documents/{document_id}/content
GET    /api/v1/verifications/{id}/evidence/{evidence_id}
GET    /api/v1/verifications/{id}/export?format={format}
DELETE /api/v1/verifications/{id}
```

Дополнительные операции, полезные прежде всего в PERSISTENT:

```text
GET  /api/v1/verifications
POST /api/v1/verifications/{id}/rerun
```

В EPHEMERAL список содержит только активные сессии, а `rerun` после очистки возвращает
`409 SOURCE_DOCUMENTS_NOT_AVAILABLE`.

### Базовые stateless tools

```text
POST /api/v1/tools/extract
POST /api/v1/tools/annotate
POST /api/v1/tools/reconcile
```

- `extract` обрабатывает один документ и возвращает текст, реквизиты, суммы и
  доказательства;
- `annotate` возвращает текстовые, координатные или ячеечные аннотации;
- `reconcile` принимает уже извлеченные операции и выполняет детерминированную
  финансовую сверку без повторного OCR.

Эти endpoints не должны создавать отдельную реализацию финансовых правил.

## Асинхронная модель без БД

OCR может занимать десятки секунд. Поэтому `POST /verifications` возвращает `202` и
идентификатор задания, а не держит один длинный запрос.

```json
{
  "verification_id": "3c58c541-0000-0000-0000-000000000000",
  "status": "QUEUED"
}
```

Состояние задания хранится в памяти одного процесса. Прогресс передается через SSE:

```text
event: progress
data: {"stage":"OCR","progress":30}

event: progress
data: {"stage":"RECONCILIATION","progress":80}

event: completed
data: {"verification_id":"3c58c541-0000-0000-0000-000000000000"}
```

До появления Redis или другого общего job store API запускается одним worker. Это
явное ограничение текущего этапа.

## Контракт результата

```json
{
  "schema_version": "1.0",
  "verification_id": "3c58c541-0000-0000-0000-000000000000",
  "status": "COMPLETED",
  "storage": {},
  "context": {},
  "summary": {},
  "findings": [],
  "articles": [],
  "documents": [],
  "evidence": [],
  "annotations": [],
  "unverified": []
}
```

`VerificationResult` является единственным источником данных для:

- информативного Markdown;
- будущего быстрого HTML-отчета;
- детального режима расследования;
- будущего PDF и XLSX-экспорта;
- внешней API-интеграции.

## Доказательства

Каждое критическое значение получает `EvidenceReference`.

```json
{
  "evidence_id": "evidence-doc-04-amount",
  "document_id": "document-04",
  "document_sha256": "...",
  "locator": {
    "type": "PAGE_REGION",
    "page": 1,
    "bbox": [0.61, 0.72, 0.19, 0.04]
  },
  "raw_text": "245 000,00",
  "normalized_value": "245000.00",
  "confidence": 0.97,
  "extractor": "tesseract"
}
```

Координаты хранятся нормализованными от `0` до `1`, чтобы не зависеть от масштаба
изображения.

| Формат | Locator |
|---|---|
| PDF/PNG | Страница и `bbox` |
| XLSX | Лист и ячейка или диапазон |
| DOCX | Таблица/строка или абзац |
| Текст | Диапазон символов |

Способ доступа к содержимому зависит от StoragePolicy:

```json
{"content_access":"CLIENT_FILE"}
```

для EPHEMERAL и

```json
{
  "content_access":"SERVER",
  "content_url":"/api/v1/verifications/run-123/documents/document-04/content"
}
```

для PERSISTENT.

## Аннотации и выделение неточностей

Оригинальный документ не редактируется. Backend возвращает аннотации, а будущий
frontend отображает их как overlay.

### Ошибка или неуверенность извлечения

`EXTRACTION_WARNING` применяется, когда:

- OCR имеет низкую уверенность;
- число содержит подозрительные буквы;
- формат суммы, даты или договора невалиден;
- найдено несколько кандидатов на одно поле;
- строку или таблицу не удалось надежно восстановить.

### Содержательное расхождение

`BUSINESS_MISMATCH` применяется, когда:

- сумма КФЗ отличается от подтвержденной суммы;
- договор не совпадает;
- документ выходит за период;
- найден дубль;
- документ нельзя однозначно отнести к статье.

OCR-предупреждение не может автоматически становиться подтвержденным финансовым
расхождением.

```json
{
  "annotation_id": "annotation-0800-report",
  "document_id": "report",
  "category": "FINANCIAL_MISMATCH",
  "severity": "ERROR",
  "message": "Сумма превышает подтвержденное значение на 12 500,00 руб.",
  "target": {
    "type": "PAGE_REGION",
    "page": 1,
    "bbox": [0.61, 0.72, 0.19, 0.04],
    "raw_text": "1 145 798,10"
  },
  "actual_value": "1145798.10",
  "expected_value": "1133298.10",
  "finding_id": "finding-0800"
}
```

## Безопасность и очистка

Минимальные требования до приемки API:

- отдельный UUID-workspace каждого запуска;
- проверка расширения, количества, размера и безопасного имени файлов;
- защита от path traversal и конфликтов имен;
- ограничения одного файла, комплекта и числа одновременных pipeline-задач;
- очистка в `finally` при успехе и исключении;
- очистка осиротевших EPHEMERAL-workspace при старте;
- очистка просроченных результатов при старте и каждом обращении к job manager;
- настраиваемый timeout каждой OCR/pipeline-стадии с контролируемой ошибкой;
- запрет содержимого документов в логах;
- отсутствие внешних OCR/LLM-вызовов;
- изоляция одновременных запусков;
- проверяемое удаление EPHEMERAL-данных;
- явная политика retention для PERSISTENT.

Проверка фактического MIME по сигнатуре, авторизация, аудит доступа и фоновый janitor
для очистки без входящих запросов остаются production-hardening задачами. Локальный
PERSISTENT поддерживается, но его нельзя выставлять в публичный контур без контроля
доступа.

## Границы текущей реализации

До отдельного решения не добавляются:

- PostgreSQL;
- Redis и Celery;
- S3/MinIO;
- постоянная авторизация пользователей;
- Google Drive OAuth;
- LLM-ассистент;
- редактирование оригиналов;
- публичный многопользовательский PERSISTENT без авторизации.

## Реализованный объем

1. Общий application layer запускает тот же OCR → registry → reconciliation pipeline.
2. Pydantic-схемы API и единый `VerificationResult` зафиксированы в коде.
3. Реализованы FastAPI, healthcheck, `/capabilities` и OpenAPI.
4. Реализованы in-memory job manager и SSE-прогресс; deployment использует один worker.
5. EPHEMERAL-workspace удаляется в `finally` и результат остается в RAM до TTL.
6. Реализованы EvidenceReference для страниц, ячеек, строк таблиц и абзацев.
7. OCR-предупреждения отделены от финансовых и реквизитных расхождений.
8. Реализованы JSON и информативный Markdown из одной модели результата.
9. PERSISTENT сохраняет документы, manifest и результат в файловом storage, поддерживает
   restart, history, rerun, delete и retention. Он принят как baseline следующего
   продуктового этапа версионирования документов.
10. Добавлены Docker-сервис `api`, unit/API-тесты и сквозной smoke-тест кейса 19.
11. Независимая black-box проверка отдельным агентом завершена; P1 очистки при restart
    исправлен и повторно проверен. Итог: 38/38 тестов, открытых P0/P1 нет.

Полный протокол: [Независимая проверка Backend API](backend-api-test-results.md).

### Запуск

```bash
docker compose up --build api
```

По умолчанию API доступен на `http://localhost:8000`, Swagger UI — на
`http://localhost:8000/docs`. Для постоянного режима:

```bash
STORAGE_MODE=persistent RETENTION_DAYS=30 docker compose up --build api
```

Timeout отдельной стадии задается через
`PIPELINE_STAGE_TIMEOUT_SECONDS` и по умолчанию равен 600 секундам.

Тесты и сквозная проверка:

```bash
docker compose run --rm tests
docker compose run --rm --entrypoint python tests /app/tests/smoke_api_case19.py
```

## Обязательный независимый этап тестирования

После реализации backend API создается **отдельный агент тестирования**, не тот агент,
который выполнял основную реализацию. Его задача — независимо проверить публичный API
как черный ящик, пройти все уже описанные сценарии и выявить расхождения между
документацией и поведением.

Тестирующий агент сначала не изменяет production-код. Он:

1. собирает образ в чистом окружении;
2. запускает API через Docker Compose;
3. читает OpenAPI и этот контракт;
4. выполняет тестовую матрицу;
5. сохраняет команды, ответы и артефакты воспроизведения;
6. формирует отчет `PASS/FAIL/BLOCKED` по каждому сценарию;
7. ранжирует дефекты по критичности;
8. проверяет, что `git status` не содержит созданных входных документов и секретов;
9. не исправляет найденные дефекты без отдельной команды пользователя.

### Матрица тестирующего агента

#### Общий API

- healthcheck и capabilities;
- OpenAPI соответствует реализованным схемам;
- загрузка допустимого комплекта;
- отклонение неподдерживаемого формата;
- лимиты размера и количества файлов;
- безопасные имена и path traversal;
- корректные HTTP-коды и структурированные ошибки;
- прогресс SSE и завершение задания;
- ручное удаление проверки;
- два одновременных запуска не видят данные друг друга.

#### Финансовые сценарии

- полный кейс 19 дает `REPORT_UNRELIABLE` и дельту 12 500,00 руб.;
- статьи `0200`, `0300`, `0900` остаются корректными;
- дубль исключается один раз;
- документ вне периода исключается;
- документ другого договора исключается;
- отсутствие источника дает `INSUFFICIENT_DATA / MISSING_DOCUMENT`;
- операция `REVIEW` не создает финансовую дельту;
- поврежденный документ дает `SOURCE_DOCUMENT_PROCESSING_INCOMPLETE`;
- OCR-строка с буквами в числе отклоняется;
- пустая детализация не становится `MISMATCH`;
- внутренняя сумма статей проверяется против итога КФЗ.

#### Evidence и annotations

- каждое критическое значение имеет источник;
- координаты PDF/PNG нормализованы;
- XLSX содержит лист и ячейку;
- DOCX содержит таблицу/строку или абзац;
- SHA-256 связывает результат с исходным документом;
- OCR warning отделен от business mismatch;
- статья `0800` содержит evidence КФЗ и всех четырех документов;
- машинное объяснение совпадает с формулой и дельтой.

#### EPHEMERAL

- документы отсутствуют в постоянном storage;
- workspace очищается после успеха;
- workspace очищается после исключения и таймаута;
- результат доступен до TTL и исчезает после TTL;
- запрос удаленного документа дает `410`;
- `rerun` без повторной загрузки дает `409`;
- рестарт не выдает старую сессию за восстановленную;
- содержимое документов не попадает в логи.

#### PERSISTENT

- документы и результат доступны после рестарта;
- история возвращает сохраненную проверку;
- повторный запуск работает без загрузки;
- evidence открывает правильную версию документа;
- удаление удаляет документы, артефакты и manifest;
- retention очищает просроченный запуск;
- EPHEMERAL и PERSISTENT используют одинаковую финансовую схему результата.

#### Отказоустойчивость

- сбой одного файла не останавливает комплект;
- stale OCR-кэш не используется после изменения SHA-256;
- прерванный запрос не оставляет вечный workspace;
- ошибка OCR возвращает контролируемый статус;
- отсутствующий отчет, контекст или правила дают понятную ошибку;
- повторная отправка не создает двойной финансовый учет.

### Формат результата агента

```text
Сценарий
Статус: PASS | FAIL | BLOCKED
Команда или HTTP-запрос
Ожидаемый результат
Фактический результат
Артефакт или фрагмент ответа
Критичность дефекта
Минимальные шаги воспроизведения
```

### Критерий завершения этапа

Backend API не считается готовым к следующему продуктово-интерфейсному этапу, пока:

- все P0-сценарии общего API проходят;
- кейс 19 воспроизводится через API;
- EPHEMERAL доказуемо очищает документы;
- PERSISTENT проходит перезапуск, удаление и retention;
- расхождения имеют валидные EvidenceReference и Annotation;
- нет критических или высоких дефектов;
- документация совпадает с фактическим поведением.

## Шаблон задачи отдельному агенту

После реализации основной агент должен создать отдельного тестирующего агента с
задачей следующего содержания:

> Независимо протестируй backend API финансовой сверки как черный ящик. Не меняй
> production-код. Собери и запусти Docker Compose в чистом окружении, проверь OpenAPI,
> оба режима хранения, полный кейс 19, неполные и поврежденные документы, evidence,
> annotations, TTL, cleanup, restart, delete, concurrency и security-негативные
> сценарии по матрице из `backend-api-storage-and-evidence.md`. Для каждого сценария
> укажи PASS/FAIL/BLOCKED, ожидаемый и фактический результат, команды и артефакты.
> Отдельно подтверди, что исходные документы не остались в EPHEMERAL и не попали в
> логи или Git. Не исправляй дефекты без отдельного разрешения пользователя.
