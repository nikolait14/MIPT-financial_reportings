# Метрики оценки решения

## Назначение документа

Документ определяет метрики сравнительного PoC, сквозного тестирования и приемки системы проверки финансовой отчетности. Метрики должны показывать, какие конкретно документы, поля и показатели обработаны правильно или неправильно, и не должны скрывать отдельные крупные ошибки за общим средним значением.

## Основное решение

Средняя дельта между извлеченными и эталонными суммами не используется.

Также не используются как критерии приемки:

- средняя знаковая ошибка;
- средняя абсолютная ошибка;
- средняя относительная ошибка;
- единый средний балл, в котором финансовые ошибки компенсируются скоростью или удобством интерфейса.

Причина: положительные и отрицательные отклонения могут взаимно компенсироваться, а усреднение абсолютных ошибок скрывает единичное критичное расхождение. Для финансовой проверки каждое критическое значение оценивается отдельно.

Пример недопустимого усреднения:

| Показатель | Ошибка, руб. |
|---|---:|
| A | +100 000,00 |
| B | -100 000,00 |
| Средняя знаковая ошибка | 0,00 |

Нулевая средняя ошибка в этом примере не означает правильную работу системы.

## Принципы оценки

1. Денежное значение либо совпало с эталоном до копейки, либо не совпало.
2. Критические реквизиты проверяются по каждому полю, а не в среднем по документу.
3. Сквозной результат считается правильным только при одновременном совпадении суммы, статуса, направления отклонения, причины и источника.
4. Пропуск ошибки и ложное срабатывание учитываются раздельно.
5. Недостаток данных и неоднозначность не считаются финансовым расхождением.
6. Результат без проверяемого доказательства не считается полностью корректным.
7. Скорость и стоимость сравниваются только среди вариантов, прошедших обязательные проверки качества.

## Уровни оценки

```text
Поле документа
      ↓
Документ
      ↓
Связь документа с показателем
      ↓
Расчет показателя
      ↓
Обнаружение расхождения
      ↓
Итоговое заключение по комплекту
```

Ошибка на нижнем уровне должна быть видна отдельно и не растворяться в итоговой оценке комплекта.

## Метрики извлечения

### Точное совпадение поля

`Field Exact Match` принимает значение 1, если нормализованное значение полностью совпадает с эталоном, и 0 в противном случае.

Отдельно считаются количество правильных и неправильных значений для каждого типа поля:

- сумма;
- дата;
- номер документа;
- номер договора;
- период;
- валюта;
- название или код показателя.

Для денежных сумм точность проверяется до копейки. Пороговое совпадение `примерно равно` не используется в итоговом расчете.

### Ошибки денежных значений

Для каждой ошибочной суммы сохраняются:

- эталонное значение;
- извлеченное значение;
- абсолютная дельта в рублях;
- направление ошибки;
- документ и поле;
- причина ошибки распознавания.

Дельты показываются построчно. Они не усредняются.

### Точность структуры таблицы

`Table Cell Exact Match` требует одновременного выполнения условий:

- значение извлечено правильно;
- значение относится к правильной строке;
- значение относится к правильной колонке;
- заголовок и единица измерения интерпретированы правильно.

Перестановка колонок считается ошибкой, даже если нужное число присутствует в распознанном тексте.

## Метрики фильтрации и связывания

### Проверка документов

По каждому документу фиксируется правильность решений:

- включить в расчет;
- исключить как дубль;
- исключить по периоду;
- исключить по договору;
- передать на ручную проверку;
- отметить технически необработанным.

Результат представляется матрицей ошибок и абсолютными количествами:

- правильно включено;
- правильно исключено;
- ошибочно включено;
- ошибочно исключено.

### Точность связывания

`Link Exact Match` равен 1, если показатель отчета связан со всеми правильными источниками и ни с одним лишним источником.

Частично правильный набор источников отмечается как отдельная ошибка и не засчитывается как точное совпадение.

### Классификация статей

Для категорий 0800, 0900 и нерелевантных документов считаются:

- количество верно классифицированных документов;
- количество ошибок по каждой паре категорий;
- precision, recall и F1 для каждой категории;
- macro F1 по категориям.

Macro F1 разрешен, поскольку он оценивает дискретную классификацию и не компенсирует денежные ошибки. Денежные суммы в эту метрику не входят.

## Метрики расчетов

### Точное совпадение показателя

`Metric Exact Match` равен 1, если одновременно совпали:

- набор входных документов;
- нормализованные входные суммы;
- правило агрегирования;
- ожидаемое значение до копейки;
- правило округления;
- подтверждающие доказательства.

### Точное совпадение расхождения

`Discrepancy Exact Match` требует одновременного совпадения:

- фактического значения отчета;
- ожидаемого значения;
- размера дельты;
- направления отклонения: завышение или занижение;
- статуса;
- reason code.

Совпадение только факта наличия ошибки без правильной суммы не засчитывается.

### Сквозное совпадение комплекта

`End to End Case Pass` равен 1 только тогда, когда все обязательные проверки сценария пройдены. Один неверный критический показатель переводит сценарий в состояние `FAIL`.

## Метрики обнаружения расхождений

Результаты разделяются на:

- `TP` — реальное расхождение найдено;
- `FP` — корректный показатель ошибочно помечен как расхождение;
- `FN` — реальное расхождение пропущено;
- `TN` — корректный показатель правильно признан корректным.

На их основе считаются:

- precision;
- recall;
- F1;
- количество ложных срабатываний `FP`;
- количество пропущенных расхождений `FN`.

Для маленького эталонного набора рядом с долями обязательно показываются абсолютные количества. Например, `0 FP из 4 корректных статей`, а не только `0%`.

## Метрики неопределенности

Отдельно оцениваются статусы `INSUFFICIENT_DATA` и `AMBIGUOUS`.

### Корректный отказ от вывода

Считаются:

- случаи, когда система правильно отказалась от вывода;
- случаи, когда система выдала уверенный, но неподтвержденный результат;
- лишние отказы при наличии достаточных данных;
- случаи, когда неоднозначность была ошибочно превращена в единственную связь.

### Неподтвержденные утверждения

`Unsupported Claim Count` — количество финансовых выводов без достаточного источника или доказательства.

Целевое значение для текущего эталона: 0.

## Метрики доказательств

### Покрытие доказательствами

`Evidence Coverage` показывает, у скольких финансовых результатов присутствует ссылка на конкретный источник.

Для полного зачета ссылка должна содержать:

- идентификатор документа;
- страницу, координаты, ячейку или абзац;
- исходный фрагмент или значение;
- связь доказательства с конкретным результатом.

### Точность доказательства

`Evidence Exact Match` равен 1, если указанный фрагмент действительно подтверждает соответствующее значение или решение.

Ссылка на правильный файл, но неправильную страницу или ячейку считается ошибкой.

## Техническая надежность

Оцениваются абсолютные количества:

- успешно обработанных файлов;
- частично обработанных файлов;
- поврежденных файлов;
- неподдерживаемых файлов;
- необработанных файлов без понятного статуса;
- случаев, когда ошибка одного файла остановила весь комплект;
- успешных повторных запусков без повторного учета документов.

Обязательное условие: ошибка одного файла не должна останавливать обработку остальных файлов комплекта.

## Производительность и стоимость

Производительность не объединяется с качеством в средний балл.

Для каждого тестового комплекта отдельно сохраняются:

- полное время обработки;
- время по компонентам;
- максимальное потребление памяти;
- использование CPU или GPU;
- количество обращений к внешним сервисам;
- стоимость внешних вызовов;
- объем переданных внешнему сервису данных.

Сравнение выполняется по таблице отдельных прогонов. Среднее время не используется как единственный показатель; дополнительно показываются минимум, медиана, максимум и каждый неуспешный прогон. Производительность рассматривается только после прохождения обязательных критериев качества.

## Обязательные проверки текущего кейса

Текущий комплект получает `PASS`, только если одновременно выполнены все условия:

| Проверка | Ожидаемый результат |
|---|---|
| Статья 0200 | 5 558 474,83 руб., `CORRECT` |
| Статья 0300 | 1 671 359,96 руб., `CORRECT` |
| Статья 0800 | Ожидаемо 1 133 298,10 руб. |
| Расхождение 0800 | Завышение на 12 500,00 руб., `MISMATCH` |
| Статья 0900 | 3 204 744,51 руб., `CORRECT` после фильтрации |
| Общий ожидаемый итог | 11 567 877,40 руб. |
| Общее расхождение | Завышение на 12 500,00 руб. |
| Документы 09 и 10 | Учтены один раз, обнаружен дубль |
| Документ 14 | Исключен как `OUT_OF_PERIOD` |
| Документ 15 | Исключен как `WRONG_CONTRACT` |
| Неполная детализация | `INSUFFICIENT_DATA`, без выдуманного значения |
| Ложные финансовые ошибки | 0 |
| Неподтвержденные утверждения | 0 |
| Доказательства | Присутствуют и корректны для каждого финансового вывода |
| Утечка эталона | Эталонный файл не использован рабочим контуром |

## Сравнение кандидатов OCR и VLM

Конкретный состав вариантов, эталонные значения и порядок запуска первого сравнения описаны в документе [PoC распознавания целевой строки КФЗ](kfz-row-extraction-poc.md).

Кандидат сначала проверяется по обязательным полям каждого документа.

Порядок выбора:

1. Исключаются кандидаты, допустившие ошибку в критической сумме, договоре, периоде или структуре проверяемой строки.
2. Среди оставшихся сравнивается количество ошибок в некритических полях.
3. Затем сравниваются доказательства и координаты.
4. Только после равенства по качеству сравниваются время, ресурсы и стоимость.

Победитель не определяется по средней дельте, среднему OCR score или единому интегральному баллу.

## Формат отчета об оценке

Каждый запуск должен формировать:

1. общий статус `PASS` или `FAIL`;
2. список обязательных проверок;
3. количество правильных и неправильных полей по типам;
4. список всех денежных ошибок с индивидуальными дельтами;
5. матрицу классификации документов;
6. TP, FP, FN и TN по расхождениям;
7. ошибки связывания;
8. результаты проверки доказательств;
9. неподтвержденные выводы и отказы от ответа;
10. технические ошибки по файлам;
11. время, ресурсы и стоимость конкретного прогона;
12. версии данных, правил, моделей и компонентов.

## Критерий перехода к следующему этапу

PoC допускается к развитию только при выполнении обязательного сквозного сценария без денежных ошибок, ложных расхождений и неподтвержденных выводов. Компонент с лучшим средним показателем, но хотя бы одной критической финансовой ошибкой, не может быть выбран победителем.
