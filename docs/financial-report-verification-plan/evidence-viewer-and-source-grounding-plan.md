# План: доказательства, просмотр источников и подсветка расхождений

## Статус

Инкремент `Source Evidence API` реализован: PDF/PNG получают сессионные
page-preview, PDF сначала проверяется на пригодный нативный текстовый слой, а
сканы OCR-ятся постранично. API выдачи документа, страницы и evidence защищены
тем же `owner_session_hash`, что и результат сверки. EPHEMERAL-workspace
сохраняется только до TTL результата для просмотра evidence и затем удаляется
целиком; при ошибке он удаляется сразу.

## Цель

Сделать вывод системы проверяемым человеком: из расхождения в отчете пользователь
должен за один переход попасть к конкретной ячейке КФЗ и фрагментам исходных
документов, из которых сформирована подтвержденная сумма.

Этап не меняет текущий финансовый вывод и не вводит постоянное хранение. В
первой web-версии документы и производные страницы доступны только владельцу
текущей EPHEMERAL-сессии и удаляются вместе с ее workspace.

## Пользовательский результат

Продукт предоставляет два представления одного результата.

### Быстрый отчет

- итоговое заключение и сумма подтвержденного расхождения;
- таблицу статей КФЗ: значение отчета, подтвержденная сумма, дельта, статус и
  количество источников;
- отдельный список `REVIEW` и `INSUFFICIENT_DATA` с понятной причиной;
- ссылку «показать доказательства» для каждой статьи или детализации.

### Детальная проверка

Для выбранной статьи пользователь видит:

```text
КФЗ:                1 145 798,10 ₽
Подтверждено:        1 133 298,10 ₽
Расхождение:          +12 500,00 ₽

[КФЗ] [Акт 1] [Акт 2] [Служебная записка]
  ↑       ↑       ↑            ↑
подсвеченные ячейка, сумма и контекст назначения расходов
```

Слева располагаются формула, статусы и объяснение; справа — листаемый источник
с выделением конкретной области. Подсветка показывает доказательство, а не
утверждает, что OCR безошибочен: метод извлечения и confidence должны быть
видимы пользователю.

## Целевая модель доказательства

Каждое нормализованное поле и каждый компонент суммы ссылаются на единый
`EvidenceReference`.

```json
{
  "evidence_id": "ev_…",
  "field": "amount",
  "value": "245000.00",
  "source": {
    "document_id": "doc_…",
    "file_name": "04_Акт_118.pdf",
    "page": 1,
    "locator": "ocr:line:8",
    "bbox": [120, 840, 310, 42],
    "raw": "Стоимость оказанных услуг: 245 000,00 руб.",
    "method": "native_pdf_text",
    "confidence": 0.97
  }
}
```

| Поле | Значение |
|---|---|
| `document_id` | Внутренний идентификатор файла в конкретной проверке |
| `page` | Номер страницы, начиная с 1; для офисных файлов может отсутствовать |
| `locator` | Стабильный адрес: строка OCR, абзац DOCX или ячейка XLSX |
| `bbox` | `[left, top, width, height]` в пикселях страницы; отсутствует, если координат нет |
| `raw` | Исходный фрагмент, который пользователь может сопоставить с документом |
| `method` | `native_pdf_text`, `native_docx`, `native_xlsx` или `ocr` |
| `confidence` | Уверенность OCR, если применимо; не выдумывается для нативных данных |

Для агрегата evidence не заменяется одним «общим» фрагментом: результат
содержит список исходных evidence и воспроизводимую формулу.

## Обработка PDF

```text
PDF
 ├── качественный текстовый слой → нативный text + координаты
 ├── скан / пустой слой          → рендер каждой страницы → OCR + bbox
 └── смешанный документ          → выбор способа отдельно для каждой страницы
```

1. PDF обрабатывается постранично; запись `page:1` больше не используется как
   универсальная заглушка.
2. Нативный текстовый слой имеет приоритет для текстового PDF: это быстрее и
   точнее OCR.
3. OCR используется только для страниц без пригодного текстового слоя или как
   управляемый fallback.
4. Если поле распознано неоднозначно или confidence ниже порога, оно не
   становится точным финансовым фактом: документ получает `REVIEW` с причиной.
5. Исходный файл не передается внешнему сервису. Рендер и OCR остаются в
   локальном Docker-контуре.

## API-контракт

Все методы требуют существующую cookie активной браузерной сессии. Идентификатор
проверки не является правом доступа: для чужой или завершенной EPHEMERAL-сессии
возвращается неразличимый `404`, а после cleanup — `410` там, где это уже
оговорено текущим API.

```text
GET /api/verifications/{verification_id}/report
GET /api/verifications/{verification_id}/documents
GET /api/verifications/{verification_id}/documents/{document_id}/pages/{page}
GET /api/verifications/{verification_id}/evidence/{evidence_id}
```

- `report` возвращает быстрый отчет, формулы и ссылки на evidence;
- `documents` возвращает метаданные, число страниц и доступные evidence;
- `pages/{page}` отдает временный поток отрендеренной страницы только в рамках
  текущей сессии, без постоянной публичной ссылки;
- `evidence/{evidence_id}` возвращает фрагмент, координаты и связь с полем
  отчета.

API не должно отдавать исходный путь на диске, статический URL без проверки
сессии или токен, пригодный после завершения проверки.

## Порядок реализации

| Шаг | Результат | Проверка готовности |
|---|---|---|
| 1. Постраничная модель | `PageArtifact`, page count, SHA-256 и способ извлечения на страницу | Многостраничный PDF не теряет вторую страницу |
| 2. Нативный PDF text layer | Координатные фрагменты текста без OCR | Текстовый PDF не запускает OCR без необходимости |
| 3. Общий `EvidenceReference` | Единый контракт для PDF, PNG, DOCX и XLSX | Любая сумма в сверке имеет источник либо явную причину отсутствия |
| 4. Evidence API | Сессионно защищенная выдача страницы и фрагмента | Чужая сессия не получает ни метаданных, ни байтов документа |
| 5. Overlays | Координаты превращаются в подсветку в viewer | Клик по дельте открывает верную страницу и область |
| 6. Два режима UI | Быстрый summary и детальный инспектор | Пользователь понимает «что, где и почему» без чтения JSON |

## Ближайший исполнимый инкремент: Source Evidence API

### Результат инкремента

Backend умеет отдать владельцу активной сессии конкретную страницу исходного
документа и связанные с ней доказательства. Frontend пока не обязан рисовать
полноценный viewer: на выходе достаточно стабильного API, `PageArtifact` и
координат для будущего overlay.

### Задачи

1. Ввести `PageArtifact` для PDF/PNG: `document_id`, номер страницы, хеш
   исходника, путь внутри workspace, размеры, способ извлечения и статус.
2. Заменить допущение `page:1` в OCR-потоке на постраничную обработку.
3. Перед OCR проверить нативный текстовый слой PDF; применить OCR лишь к
   странице без пригодного слоя.
4. Нормализовать текущие доказательства в `EvidenceReference` с `page`,
   `locator`, `bbox`, `raw`, `method` и опциональным `confidence`.
5. Добавить защищённые методы выдачи списка документов, страницы и evidence.
6. Добавить black-box и unit-тесты ниже.

### Минимальный API

```text
GET /api/verifications/{verification_id}/documents
GET /api/verifications/{verification_id}/documents/{document_id}/pages/{page}
GET /api/verifications/{verification_id}/evidence/{evidence_id}
```

Первый метод возвращает только метаданные и доступные страницы. Второй отдает
страницу как сессионный поток, третий — JSON-доказательство. Во всех трех
случаях проверяется `owner_session_hash`; чужой `verification_id` не раскрывает
даже существование файла.

### Definition of Done

- PDF из двух страниц возвращает две `PageArtifact`, а не только первую;
- текстовая страница имеет `method: native_pdf_text`, сканированная — `ocr`;
- каждая сумма, участвующая в статье сверки, содержит evidence либо явную
  причину его отсутствия;
- запрос владельца получает корректную страницу и bbox;
- аналогичный запрос из другой сессии получает `404` без байтов или метаданных;
- по окончании EPHEMERAL-сессии страницы и evidence недоступны;
- полный кейс 19 сохраняет финансовый результат `+12 500,00` по `0800`.

### Явно вне инкремента

- React/HTML viewer и интерактивный overlay;
- публичные ссылки на файлы;
- хранение документов после завершения EPHEMERAL-сессии;
- новые правила классификации неподдерживаемых статей.

## Обязательные тесты

- текстовый одно- и многостраничный PDF;
- сканированный многостраничный PDF;
- смешанный PDF: одна текстовая и одна сканированная страница;
- некорректный OCR confidence и отсутствующий `bbox`;
- отсутствие evidence: `REVIEW` / `INSUFFICIENT_DATA`, не ложное `CORRECT`;
- открытие evidence владельцем и попытка доступа из другой сессии;
- отсутствие доступа после EPHEMERAL cleanup;
- соответствие bbox фактической отрендеренной странице.

## Вне текущего этапа

- постоянный архив доказательств и история версий: только после явной функции
  «Сохранить в проект» и полноценной аутентификации;
- автоматическая правка исходного документа;
- внешний OCR/VLM-сервис;
- ручное редактирование сумм без сохранения аудиторского следа.
