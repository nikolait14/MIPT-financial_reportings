# PoC распознавания целевой строки КФЗ

## Статус

- Этап: локальный OCR-baseline выполнен 12 ноября 2026 года.
- Объект: одна целевая строка итоговой карточки учета фактических затрат.
- Реализация: region-first baseline реализован и проверен.
- Код: находится в `poc/kfz-row-extraction`.
- Обучение моделей: не требуется.

Фактические результаты приведены в документе [Результаты PoC распознавания строки КФЗ](kfz-row-extraction-results.md).

## Цель

Проверить, можно ли надежно извлечь значения строки `3 этап, 2026 г.` из файла `01_Карточка_учета_фактических_затрат_этап_3.pdf`, несмотря на мелкий текст и плотную структуру таблицы.

PoC должен выбрать технический способ извлечения, который:

- находит правильную строку;
- сохраняет соответствие между значениями и колонками;
- извлекает критические суммы точно до копейки;
- возвращает координаты доказательства;
- явно отказывается от ответа при расхождении методов;
- воспроизводит результат при повторном запуске.

PoC не проверяет первичные документы, не классифицирует расходы по статьям и не формирует итоговое заключение по комплекту. Эти задачи начинаются только после снижения риска распознавания КФЗ.

## Контекст проверки

Официальные параметры задания передаются системе как входной контекст, а не извлекаются из эталонного файла.

```yaml
report_file: 01_Карточка_учета_фактических_затрат_этап_3.pdf
target_row_label: 3 этап, 2026 г.
contract_number: 24/03/15-01
period_from: 2026-01-01
period_to: 2026-05-31
```

В целевой архитектуре эти параметры образуют сущность `VerificationContext`:

| Поле | Назначение |
|---|---|
| `report_file` | Итоговый отчет, содержащий проверяемый показатель |
| `target_row_label` | Строка или период, который необходимо проверить |
| `contract_number` | Договор для отбора первичных документов |
| `period_from` | Начало допустимого периода |
| `period_to` | Конец допустимого периода |

Параметры должны быть конфигурируемыми. Значения кейса 19 нельзя зашивать внутрь алгоритма распознавания.

## Почему нужен отдельный PoC

На странице КФЗ одновременно присутствуют:

- мелкий шрифт;
- много близко расположенных числовых колонок;
- многоуровневые заголовки;
- тонкие границы ячеек;
- высокий риск перестановки значений между соседними колонками;
- одна проверяемая строка среди других периодов и итогов.

Полностраничный ответ VLM может выглядеть правдоподобно, но содержать ошибку в одной цифре или колонке. Поэтому успех оценивается по каждой ячейке, а не по общему впечатлению от распознанного текста.

## Критические поля

Все денежные ячейки и их принадлежность колонкам являются критическими. Особый контроль применяется к:

- статье 0200;
- статье 0300;
- статье 0800;
- статье 0900;
- итогу строки;
- метке этапа и года.

Значение, извлеченное правильно, но присвоенное соседней колонке, считается критической ошибкой.

## Сравниваемые варианты

### Вариант A Region first OCR

```text
PDF
 ↓
Рендер страницы 300 400 и 600 DPI
 ↓
Поиск области таблицы
 ↓
Поиск строки 3 этап 2026 г.
 ↓
Определение вертикальных границ ячеек
 ↓
Увеличение отдельных ячеек
 ↓
OCR чисел
 ↓
Нормализация и проверка
```

Назначение варианта: получить максимально контролируемое извлечение чисел без передачи всей плотной страницы одной модели.

### Вариант B Region first document VLM

```text
PDF
 ↓
Рендер страницы в высоком разрешении
 ↓
Выделение заголовков и целевой строки
 ↓
Передача отдельных фрагментов документной VLM
 ↓
Структурированный результат по заданной схеме
 ↓
Проверка координат и типов значений
```

Основной локальный кандидат: PaddleOCR-VL. Альтернативный локальный кандидат может быть добавлен после проверки требований к ресурсам и лицензии.

### Вариант C Full page VLM baseline

Полная страница передается документной VLM с запросом на извлечение целевой строки. Вариант используется только как baseline, чтобы измерить риск перестановки колонок и потери мелких значений.

Вариант C не выбирается основным, если он не возвращает проверяемые координаты каждой ячейки или нестабилен при повторном запуске.

## Рекомендуемый рабочий вариант

Основной кандидат на итоговую схему — комбинация A и B:

1. VLM или layout-модель определяет структуру, заголовки и границы целевой строки.
2. Числовой OCR независимо читает увеличенные ячейки.
3. VLM извлекает значения из тех же фрагментов в структурированном формате.
4. Результаты сравниваются по каждой критической ячейке.
5. Совпавшие значения проходят детерминированные проверки.
6. Несовпавшие значения получают `AMBIGUOUS` и не принимаются автоматически.

Ни один из двух методов не является безусловным источником истины.

## Предобработка

Для каждого варианта фиксируются параметры, чтобы результат можно было воспроизвести:

- разрешение рендера;
- цветной или монохромный режим;
- контрастирование;
- устранение наклона;
- удаление шума;
- масштабирование фрагмента;
- координаты таблицы;
- координаты целевой строки;
- способ определения границ колонок.

Предобработка не должна изменять цифры или дорисовывать отсутствующие символы генеративным способом.

## Канонический результат PoC

Для каждой ячейки кандидат должен вернуть:

```json
{
  "row_label": "3 этап, 2026 г.",
  "metric_code": "0800",
  "metric_name": "Общепроизводственные затраты",
  "raw_value": "1 145 798,10",
  "normalized_value": "1145798.10",
  "page": 1,
  "bbox": [0, 0, 0, 0],
  "method": "region_ocr",
  "confidence": null,
  "status": "EXTRACTED"
}
```

`bbox` в примере является заполнителем формата. Реальный результат должен содержать координаты фактической ячейки.

## Детерминированные проверки

После распознавания выполняются проверки:

- денежный формат содержит не более двух знаков после запятой;
- пробелы и разделители нормализованы без изменения значения;
- все значения принадлежат целевой строке;
- каждому значению соответствует ровно одна колонка;
- отсутствуют дубли одной ячейки;
- итог строки согласуется с суммой верхнеуровневых статей;
- внутренние подколонки проверяются на арифметическую согласованность там, где структура формы задает такое правило.

Арифметическая согласованность является контрольным сигналом. Она не дает права автоматически исправлять распознанную цифру.

## Правила сравнения

Средняя дельта, MAE и средняя относительная ошибка не используются.

Для каждой ячейки фиксируются:

- `EXACT_MATCH` или `MISMATCH`;
- эталонное значение;
- извлеченное значение;
- индивидуальная дельта;
- правильность строки;
- правильность колонки;
- правильность координат доказательства.

Результаты разных DPI и методов показываются отдельными строками и не усредняются.

## Критерии PASS

Вариант получает `PASS`, только если одновременно выполнены условия:

1. Найдена строка `3 этап, 2026 г.`.
2. Все критические значения совпали с эталоном до копейки.
3. Все значения связаны с правильными колонками.
4. Для каждого значения сохранены корректные координаты.
5. Нет неподтвержденных или автоматически угаданных значений.
6. Повторный запуск на тех же входных данных дает тот же результат.
7. Эталонный файл не был доступен контуру извлечения.

Одна критическая ошибка означает `FAIL` для варианта.

## Правила выбора победителя

1. Варианты с `FAIL` исключаются независимо от скорости.
2. Если `PASS` получил один вариант, он выбирается для первого вертикального среза.
3. Если `PASS` получили несколько вариантов, сначала сравниваются доказательства и воспроизводимость.
4. После равенства по качеству сравниваются время, память, требования к GPU и стоимость.
5. Full page VLM не получает преимущество только из-за меньшего количества этапов.

## Протокол запуска

Для каждого варианта необходимо сохранить:

- название и версию модели;
- версию библиотек;
- параметры рендера и предобработки;
- использованный промпт;
- структурированный результат;
- изображение с отмеченными координатами ячеек;
- таблицу точных совпадений;
- список ошибок;
- время и ресурсы конкретного запуска;
- общий статус `PASS` или `FAIL`.

PoC должен быть повторен не менее трех раз с одинаковыми параметрами для проверки стабильности. Результаты повторов не усредняются: каждый прогон обязан пройти обязательные проверки.

## Решение после PoC

### Если есть PASS

- выбранный способ включается в первый вертикальный срез;
- фиксируется схема выходных данных;
- начинается обработка реквизитов первичных документов;
- добавляются фильтры договора, периода и дублей.

### Если PASS нет

- проверяется наличие исходного цифрового отчета в XLSX или другом структурированном формате;
- добавляется пользовательское подтверждение строки;
- значения с расхождением методов не используются автоматически;
- универсальная обработка всего комплекта не начинается до определения безопасного пути.

## Условия начала реализации

Перед написанием кода необходимо отдельно согласовать:

- разрешение на реализацию PoC;
- допустимость локальной установки выбранных моделей;
- доступные CPU, GPU и память;
- допустимость использования внешнего API для открытого набора;
- место хранения временных изображений и результатов;
- формат итогового отчета PoC.
