# Linux OCR и Docker: решение и результаты

## Принятое решение

Для извлечения строки `3 этап, 2026 г.` на Linux выбран двухконтурный локальный OCR:

| Роль | Провайдер | Режим | DPI | Причина выбора |
|---|---|---|---:|---|
| Основной | PaddleOCR 3.7.0, `PP-OCRv5_mobile_det` + `eslav_PP-OCRv5_mobile_rec` | поиск строки, геометрия таблицы, повторный OCR 15 ячеек | 300 | 15/15 точных значений в 3/3 повторах; минимальный успешно проверенный DPI |
| Резервный | Tesseract 5.5.0, `rus+eng` | full-page OCR, сборка подписи строки из отдельных слов, геометрия таблицы | 400 | 15/15 точных значений в 3/3 повторах; независимый OCR-движок |

Apple Vision сохраняется как macOS-baseline, но не входит в Linux runtime. Тяжелая VLM и локальная LLM для извлечения этой строки не требуются: текстовый итог формируется из структурированного результата сверки, а финансовые вычисления остаются детерминированными.

## Проверка качества

Эталон использовался только в `poc/linux-ocr-benchmark/run_benchmark.py` для оценки. Production-команда `financial_verification.report_ocr_pipeline` не читает эталонные суммы и проверяет только полноту и числовой формат 15 полей.

| Провайдер | DPI | Подготовка строки | Full-page 15/15 | Region-first 15/15 | Решение |
|---|---:|---|---:|---:|---|
| PaddleOCR | 300 | PASS | 3/3 | 3/3 | основной |
| PaddleOCR | 400 | PASS | 3/3 | 3/3 | повторный режим |
| PaddleOCR | 600 | PASS | 3/3 | 3/3 | повторный режим |
| Tesseract | 300 | FAIL | 0/3 | 0/3 | не использовать |
| Tesseract | 400 | PASS | 3/3 | 0/3 | full-page fallback |
| Tesseract | 600 | FAIL | 0/3 | 0/3 | не использовать |

Критерий приемки — точное совпадение каждой ячейки до копейки во всех повторах. Средняя ошибка не используется. Финальная матрица находится в `artifacts/linux-ocr-benchmark/benchmark.json` и `benchmark.md` и генерируется повторно одной командой.

В ходе эксперимента серверный детектор PaddleOCR завершался `OOMKilled` с кодом 137. Поэтому в CPU-образе закреплен мобильный детектор. Это не снизило точность на текущем эталоне и сделало потребление памяти приемлемым.

## Production-поток

```text
PDF отчета
  → Poppler, страница 1 в 300 DPI
  → PaddleOCR full page
  → поиск подписи строки по этапу и году
  → детерминированное определение границ таблицы
  → контактный лист из 15 ячеек
  → PaddleOCR числовых областей
  → report-ocr.json + extraction.json + изображения доказательств
  → существующая детерминированная сверка
```

Если основной провайдер не смог получить все 15 числовых полей, автоматически запускается Tesseract 400 DPI. Его full-page наблюдения проецируются в тот же контракт контактного листа, поэтому модуль сверки не зависит от OCR-движка.

Фактическая проверка отказа основного провайдера завершилась успешно: `fallback_used=true`, Tesseract извлек 15/15 полей, после чего результат прошел тот же точный evaluation.

## Контейнер

- базовый образ: закрепленный digest `python:3.11-slim`;
- архитектура проверенного образа: `linux/arm64`;
- размер локального образа: около 443 МБ;
- PaddlePaddle 3.2.2;
- PaddleOCR 3.7.0;
- Tesseract 5.5.0 с `rus` и `eng`;
- модели PaddleOCR загружены при сборке, runtime не требует сети;
- исходные документы подключаются read-only, артефакты — отдельным writable volume.

## Запуск

Production-экстракция без эталона:

```bash
docker compose build report-ocr
docker compose run --rm report-ocr
```

Строгий evaluation основного и резервного движков:

```bash
docker compose run --rm ocr-benchmark
```

Полученный production-артефакт: `artifacts/linux-report-ocr/report-ocr.json`. Скрипт сверки автоматически предпочитает его macOS-артефакту:

```bash
bash scripts/run_case19_reconciliation.sh
```

## Границы результата

- Проверен один отчет и одна строка; это не оценка качества на всех шаблонах КФЗ.
- Для новых шаблонов необходим отдельный размеченный набор и тот же строгий cell-level evaluation.
- Tesseract квалифицирован только как full-page fallback при 400 DPI.
- Низкая уверенность, отсутствие ячейки или нечисловое значение должны приводить к повторному режиму либо `FAIL`, а не к подстановке ожидаемой суммы.
- Контейнеризация API, очереди обработки и пользовательского интерфейса остаются следующим продуктовым этапом; текущий образ закрывает переносимый OCR-контур.
