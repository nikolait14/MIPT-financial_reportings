## Итог

Этап `нормализация операций → классификация → агрегирование → сверка` реализован 12 ноября 2026 года и усилен проверками неполных данных 14 ноября 2026 года.

## Реализованный поток

```text
отфильтрованный реестр документов
             +
извлеченный текст и сумма
             ↓
нормализованная операция
             ↓
версионируемые смысловые правила
             ↓
CLASSIFIED или REVIEW
             ↓
Decimal-агрегирование по статье
             +
значения строки КФЗ из raw OCR
             ↓
CORRECT / MISMATCH / INSUFFICIENT_DATA
             ↓
заключение и цепочки доказательств
```

## Классификация

Правила находятся в `config/cost-article-rules.json` и имеют версию `cost-articles-v1`. Решение строится по содержанию операции:

- заголовок расчетной ведомости, коды `0201/0202` и зарплатная лексика для `0200`;
- заголовок расчета, код `0300` и лексика страховых взносов для `0300`;
- производственное назначение, обслуживание, калибровка и измерительное оборудование для `0800`;
- административное, управленческое, ИТ- и коммуникационное обеспечение для `0900`.

Имя файла не используется как самостоятельное основание классификации. Для каждого совпавшего признака сохраняются идентификатор правила, вес, исходный текст и locator. Если минимальный балл не набран или две статьи получили одинаковый лучший балл, операция получает `REVIEW` с `NO_CLASSIFICATION_SIGNAL` или `AMBIGUOUS_CLASSIFICATION`.

Модель или внешний API на этом наборе не требуются. В будущем семантическая модель может быть резервным классификатором только для операций, оставшихся в `REVIEW`.

## Защита от задвоения и утечки эталона

Классифицируются только документы, которые уже получили `INCLUDE`. Поэтому в расчет не попадают:

- точная копия документа 09 — `DUPLICATE_DOCUMENT`;
- документ 14 за июнь — `OUT_OF_PERIOD`;
- документ 15 по другому договору — `WRONG_CONTRACT`.

Файл `!Правильные_ответы_и_разбор.xlsx` исключается реестром до извлечения содержимого. Рабочий модуль не открывает его и не получает из него суммы. Значения КФЗ читаются из сырого результата region-first OCR `region-run-1.json`; поля `expected` из оценочного PoC рабочий модуль не использует.

## Финансовый результат

Все денежные вычисления выполняются через `Decimal` с точностью до копейки.

| Статья | По КФЗ, руб. | По документам, руб. | КФЗ минус документы, руб. | Статус |
|---|---:|---:|---:|---|
| 0200 | 5 558 474,83 | 5 558 474,83 | 0,00 | `CORRECT` |
| 0300 | 1 671 359,96 | 1 671 359,96 | 0,00 | `CORRECT` |
| 0800 | 1 145 798,10 | 1 133 298,10 | 12 500,00 | `MISMATCH / REPORT_OVERSTATED` |
| 0900 | 3 204 744,51 | 3 204 744,51 | 0,00 | `CORRECT` |
| **Итого** | **11 580 377,40** | **11 567 877,40** | **12 500,00** | **`MISMATCH / REPORT_OVERSTATED`** |

Средняя дельта не рассчитывается. Каждая статья проверяется отдельно и точно до копейки.

Внутренняя арифметика КФЗ также проверяется отдельно: сумма `0200 + 0300 + 0800 + 0900`
равна итоговой строке — 11 580 377,40 руб., статус
`CORRECT / REPORT_TOTAL_CONSISTENT`. Эта проверка не заменяет сверку с первичными
документами, но обнаруживает часть ошибок OCR и внутренние противоречия отчета.

## Безопасная обработка неполных данных

- отсутствие документов дает `INSUFFICIENT_DATA / MISSING_DOCUMENT`, а не сравнение с нулем;
- при наличии операции в `REVIEW` агрегируется только классифицированная часть, дельта не выводится;
- технически необработанный источник дает `SOURCE_DOCUMENT_PROCESSING_INCOMPLETE` и перечисляется в человекочитаемом отчете;
- отсутствие источников настроенной детализации дает `MISSING_DETAIL_SOURCE`;
- OCR-значение с буквами или посторонним текстом отклоняется вместо удаления символов;
- неизвестные подтвержденные значения представлены как `null`, а не как `0.00`.

Эти правила покрыты независимыми синтетическими unit-тестами и не требуют артефактов
кейса 19.

### Ограничение, связанное с ОСВ

По разъяснению организаторов оборотно-сальдовая ведомость не входит в комплект данных
хакатона и дополнение набора не планируется. Поэтому ее отсутствие не является
`MISSING_DOCUMENT`. Сверка выполняется по выданным первичным и расчетным документам, а
непроверяемые без дополнительного регистра показатели остаются
`INSUFFICIENT_DATA / INSUFFICIENT_DETAIL`.

Обнаруженное завышение статьи 0800 на 12 500,00 руб. не зависит от наличия ОСВ: оно
полностью подтверждается сравнением КФЗ с четырьмя предоставленными документами статьи.
Возможное подключение ОСВ относится к production-roadmap и должно использоваться как
дополнительный независимый контур контроля полноты.

## Внутренняя детализация

Из зарплатных ведомостей дополнительно извлекаются явные строки с кодами затрат:

- сумма `0201` подтверждает основную заработную плату 5 054 470,26 руб.;
- сумма `0202` подтверждает совместное значение дополнительной заработной платы и резерва отпусков 504 004,57 руб.

Источники не позволяют независимо разделить `0202` на дополнительную зарплату и резерв. Эти два отдельных поля, а также неподтвержденные подстатьи страховых взносов, трудоемкость, материалы и оплата без резерва получают `INSUFFICIENT_DATA / INSUFFICIENT_DETAIL`. Совместная сумма `0202` при этом подтверждается отдельной проверкой. Недостаток детализации не превращается в финансовое расхождение.

## Доказательства

Для каждой статьи результат содержит:

- значение из КФЗ и OCR-координаты;
- перечень операций и идентификаторы документов;
- сумму и locator ячейки, абзаца или OCR-блока;
- совпавшие смысловые правила и исходные фрагменты;
- формулу агрегирования;
- точную дельту, направление и reason code.

## Запуск и артефакты

После реестра и OCR КФЗ этап запускается командой:

```bash
bash scripts/run_case19_reconciliation.sh
```

Создаются:

- `artifacts/case19-reconciliation/reconciliation.json` — полный машиночитаемый результат;
- `artifacts/case19-reconciliation/operation-ledger.csv` — реестр операций и решений;
- `artifacts/case19-reconciliation/reconciliation.md` — человекочитаемое заключение.

Производные артефакты исключены из Git и воспроизводятся локально.

## Автоматические проверки

Тесты проверяют:

- классификацию по содержанию без опоры на имя файла;
- безопасный отказ для неизвестной и неоднозначной операции;
- чтение значений отчета из сырого OCR, а не из эталонных полей PoC;
- безопасный статус при полном или частичном отсутствии подтверждающих документов;
- согласованность `REVIEW`-операций, статей и итога;
- пустую детализацию без ложного финансового расхождения;
- отказ на буквенных OCR-ошибках в числах;
- равенство суммы статей и итоговой строки отчета;
- распределение `5/5/4/5` по четырем статьям;
- точные суммы и единственное расхождение 12 500,00 руб.;
- фильтры дубля, периода и договора;
- отсутствие oracle в операциях;
- наличие доказательств суммы и классификации;
- подтверждаемую и неподтверждаемую внутреннюю детализацию.

Полный набор из тестов реестра и сверки запускается командой:

```bash
PYTHONPATH=src python3 -m unittest discover -v tests
```
