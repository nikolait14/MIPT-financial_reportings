# План постоянного хранения и версионирования документов

## Решение текущего этапа

Целевой продуктовый режим следующей итерации — `PERSISTENT`. Пользователь должен
возвращаться к ранее загруженным комплектам, повторно открывать результаты проверки и
видеть историю изменений документов.

Ограничение кейса относится к передаче данных во внешние API: конфиденциальные данные
нельзя отправлять внешним OCR, LLM и другим сервисам. Дополнительный запрет на локальное
постоянное хранение в кейсе не указан. Поэтому хранение реализуется внутри локального
deployment без сторонних сервисов. `EPHEMERAL` сохраняется как поддерживаемая политика
для окружений, где постоянное хранение запрещено внутренними правилами заказчика.

Текущий файловый PERSISTENT уже технически поддерживает сохранение запуска,
восстановление после рестарта, историю запусков, повторную обработку, retention и
удаление. Следующая итерация превращает этот технический режим в продуктовую систему
версий документов.

## Продуктовая модель

Метафора «Git для документов» означает не хранение PDF, DOCX и XLSX в обычном Git, а
знакомые пользователю свойства контроля версий:

- документ имеет постоянный логический идентификатор;
- каждая новая загрузка создает неизменяемую версию;
- одинаковые байты определяются по SHA-256 и не дублируются физически;
- каждая проверка фиксирует точный snapshot версий входных документов, контекста и
  правил;
- пользователь видит автора или источник, время, причину и результат изменения;
- можно сравнить две версии документа или две проверки;
- «восстановление» старой версии создает новую текущую версию и не переписывает историю;
- удаление и окончательная очистка подчиняются явной retention-политике.

Это дает три продуктовых сценария:

1. **Повторная проверка.** Пользователь открывает старый комплект и запускает его снова
   с новой версией правил или OCR.
2. **Расследование изменения.** Пользователь видит, какой документ, реквизит или сумма
   изменились и почему изменилось заключение.
3. **Аудиторский snapshot.** Итог проверки можно воспроизвести по точным версиям
   документов, правил и извлеченных значений.

## Граница текущего этапа

В текущую реализацию входят:

- локальный single-node deployment без внешних сервисов;
- проекты или комплекты документов;
- неизменяемые версии и content-addressed blob storage;
- история версий и запусков;
- сравнение метаданных, извлеченных полей и финансовых результатов;
- повторный запуск по сохраненному snapshot;
- soft delete, окончательное удаление и retention;
- аудит технических действий;
- обратная совместимость существующего API проверки.

Не входят в этот этап:

- совместное редактирование содержимого документов;
- Git-ветки, merge и разрешение конфликтов;
- облачные S3/MinIO и PostgreSQL;
- Google Drive OAuth;
- полнотекстовый поиск по архиву;
- публичный многопользовательский deployment.

Для публичного production-развертывания дополнительно обязательны авторизация,
изоляция пользователей, шифрование, управление ключами и аудит чтения документов.

## Целевая системная модель

```text
Project
  ├── Document
  │     ├── DocumentVersion 1 ── Blob sha256:A
  │     ├── DocumentVersion 2 ── Blob sha256:B
  │     └── DocumentVersion 3 ── Blob sha256:B  (без копии blob)
  │
  └── VerificationRun
        ├── RunDocumentSnapshot → точные DocumentVersion
        ├── VerificationContext
        ├── RuleSetVersion
        ├── VerificationResult
        └── EvidenceReference
```

Основные сущности:

| Сущность | Назначение |
|---|---|
| `Project` | Граница комплекта, истории и retention |
| `Document` | Логический документ с постоянным ID |
| `DocumentVersion` | Неизменяемая версия файла и извлеченных реквизитов |
| `Blob` | Файл, адресуемый по SHA-256 |
| `VerificationRun` | Зафиксированный запуск сверки |
| `RunDocumentSnapshot` | Точные версии входа конкретного запуска |
| `VersionDiff` | Изменения файла, реквизитов, сумм и статусов |
| `AuditEvent` | Загрузка, запуск, восстановление, удаление и очистка |

Для metadata repository предлагается SQLite: он остается локальным, не требует
отдельного сервиса и дает транзакции, индексы и миграции. Файлы хранятся отдельно в
content-addressed filesystem. Интерфейсы repository сохраняются так, чтобы позднее
заменить SQLite на PostgreSQL, а filesystem — на S3-совместимое хранилище.

## План реализации

### Шаг 1 Контракты и миграции

- зафиксировать схемы перечисленных сущностей и состояния lifecycle;
- определить, как существующий `verification_id` связывается с `project_id` и snapshot;
- добавить версию схемы storage и идемпотентные миграции;
- описать правила определения «того же логического документа»;
- сохранить совместимость текущих endpoints `/api/v1/verifications`.

Результат: схема данных, migration contract и тестовые fixtures без изменения
финансовой логики.

### Шаг 2 Content addressed storage

- сохранять blob по SHA-256 и проверять хеш после записи;
- записывать через временный файл с атомарным rename;
- не создавать вторую копию идентичного blob;
- отделить ссылку версии от физического файла;
- реализовать reference counting или безопасный garbage collection;
- исключить частично записанные версии после сбоя.

Результат: воспроизводимое и дедуплицированное файловое хранилище.

### Шаг 3 Repository истории

- добавить локальный SQLite repository;
- реализовать проекты, документы, версии, snapshots и audit events;
- перенести существующие manifest/result в новую модель;
- восстановить незавершенный запуск как контролируемый `FAILED`, не теряя его историю;
- оставить EPHEMERAL repository отдельной реализацией того же интерфейса.

Результат: история не зависит от памяти процесса и доступна после рестарта.

### Шаг 4 Публичный API версий

Добавить endpoints:

```text
POST   /api/v1/projects
GET    /api/v1/projects
GET    /api/v1/projects/{project_id}
POST   /api/v1/projects/{project_id}/documents
GET    /api/v1/projects/{project_id}/documents
GET    /api/v1/documents/{document_id}/versions
GET    /api/v1/documents/{document_id}/versions/{version_id}
GET    /api/v1/documents/{document_id}/compare?from={a}&to={b}
POST   /api/v1/documents/{document_id}/restore/{version_id}
GET    /api/v1/verifications/{verification_id}/snapshot
GET    /api/v1/verifications/compare?from={a}&to={b}
DELETE /api/v1/projects/{project_id}
```

Существующий `POST /api/v1/verifications` продолжает работать. Для нового продуктового
сценария он принимает `project_id` либо создает проект автоматически.

Результат: frontend может реализовать историю без доступа к внутренней структуре
storage.

### Шаг 5 Сравнение и восстановление

- сравнивать хеш и бинарный факт изменения;
- сравнивать номер, договор, период, сумму и извлеченный текст;
- сравнивать решения INCLUDE, EXCLUDE, REVIEW;
- сравнивать статьи, подтвержденные суммы, дельты и итоговое заключение;
- показывать причины изменения результата;
- восстановление старой версии оформлять новой версией с `restored_from_version_id`.

Результат: продуктовый diff, понятный финансовому специалисту, а не только разработчику.

### Шаг 6 Lifecycle и защита данных

- определить retention на уровне проекта;
- реализовать soft delete и отдельную окончательную очистку;
- не удалять blob, пока на него ссылается хотя бы один snapshot;
- очищать просроченные данные фоновым janitor;
- не писать имена, текст и содержимое документов в application logs;
- добавить локальный deployment profile `persistent` и явное предупреждение, что
  публичная сеть без авторизации не поддерживается.

Результат: предсказуемый lifecycle без потери воспроизводимости.

### Шаг 7 Тестирование и приемка

- миграция старого файлового PERSISTENT;
- две версии одного документа и дедупликация одинаковых байтов;
- snapshot остается воспроизводимым после появления новой версии;
- diff документа и двух результатов сверки;
- restore создает новую версию и не меняет старую;
- restart, конкурентные загрузки и атомарность записи;
- soft delete, purge, retention и garbage collection;
- отсутствие межпроектного доступа;
- полный кейс 19 без изменения финансового результата;
- отдельная black-box проверка тестирующим агентом.

## Критерии приемки

Этап считается завершенным, когда:

1. старый и новый API воспроизводят кейс 19 с дельтой 12 500,00 руб.;
2. повторная загрузка одинакового файла не создает второй blob;
3. каждая проверка ссылается на неизменяемый snapshot входных версий;
4. сравнение объясняет изменение реквизитов и финансового заключения;
5. restore не переписывает историю;
6. данные восстанавливаются после рестарта;
7. delete, retention и garbage collection не удаляют используемые evidence;
8. конфиденциальные данные не уходят во внешние API и не попадают в логи;
9. автоматические и независимые black-box тесты не имеют открытых P0/P1.

## Решения для согласования перед кодом

1. Используем SQLite как локальный metadata repository текущего этапа.
2. Единица истории — `Project` с логическими документами и их версиями.
3. Загрузка измененного файла создает новую версию автоматически.
4. Восстановление старой версии создает новую версию, а не перемещает указатель назад.
5. Для локальной демонстрации включаем PERSISTENT deployment profile; EPHEMERAL
   сохраняем как поддерживаемую альтернативу.
6. Сравнение в первой версии ограничиваем реквизитами, суммами, статусами и результатами
   сверки; визуальный pixel diff откладываем.
