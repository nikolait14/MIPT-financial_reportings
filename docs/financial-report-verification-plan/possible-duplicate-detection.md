# Поиск вероятных пересохраненных дублей

## Цель

Точный SHA-256 надежно находит только одинаковые байты. Если пользователь
пересохранил PDF, экспортировал тот же документ заново или добавил служебную
страницу, хеш меняется, хотя хозяйственная операция может оставаться той же.

Система дополняет точный поиск безопасным поиском **вероятных** дублей. Он не
является автоматическим удалением документа и не использует внешние сервисы
или модель: решение строится на извлеченных бизнес-реквизитах.

## Два уровня решения

| Уровень | Условие | Результат |
|---|---|---|
| Точный дубль | Совпадает SHA-256 | `EXCLUDE / DUPLICATE_DOCUMENT`; документ не участвует в сумме. |
| Вероятный пересохраненный дубль | Совпали номер, договор, сумма и дата либо полный период; байты различаются | `REVIEW / POSSIBLE_DUPLICATE_DOCUMENT`; документ не суммируется до ручного решения. |

Только совпадения всех четырех сильных реквизитов дают сигнал. Совпавшие сумма
и договор сами по себе не достаточны: для одного договора обычны несколько
документов на одну сумму. Номер отсутствует, сумма не извлечена, дата/период
не определены или есть техническая ошибка — пара не считается вероятным
дублем.

## Данные результата

Для кандидата реестр сохраняет:

```json
{
  "decision": "REVIEW",
  "reason_code": "POSSIBLE_DUPLICATE_DOCUMENT",
  "possible_duplicate_of": "document-id-original",
  "possible_duplicate_match_fields": [
    "document_number",
    "contract_number",
    "amount",
    "document_date"
  ]
}
```

В JSON/API появляется `POSSIBLE_DUPLICATE` annotation, а Markdown-отчет
перечисляет такие документы в разделе «Документы, требующие проверки».

## Почему это REVIEW, а не EXCLUDE

Два файла могут разделять номер, сумму, договор и дату из-за ошибки ввода,
корректировки или особенности документооборота. Автоматическое исключение в
этом случае создало бы риск ложного занижения подтвержденной суммы. Поэтому
система:

1. не включает кандидата в финансовое агрегирование;
2. не утверждает, что он точно дублирует исходник;
3. показывает пару и совпавшие реквизиты пользователю;
4. переводит зависимый финансовый вывод в режим недостаточности данных, если
   без кандидата полнота подтверждения не доказана.

## Границы первой версии

- Нет fuzzy text similarity, OCR-эмбеддингов и автоматического сравнения
  изображений: они создают больше ложных совпадений и требуют отдельной
  оценки качества.
- Семантическая близость текста может стать вторым сигналом в будущем, но не
  должна понижать порог из четырех сильных реквизитов без измерений на
  размеченном наборе.
- Ручное подтверждение/отклонение пары и переагрегирование относятся к
  следующему продуктово-аккаунтному этапу.

## Приемка

- Одинаковые байты остаются `DUPLICATE_DOCUMENT`.
- Два разных файла с одинаковыми четырьмя реквизитами становятся
  `POSSIBLE_DUPLICATE_DOCUMENT / REVIEW`.
- Совпадение только договора и суммы не блокирует документ.
- Кандидат не попадает в `INCLUDE` и не удваивает финансовую сумму.
