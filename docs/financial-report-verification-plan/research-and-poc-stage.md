# Этап исследования и выбора решения

## Статус документа

- Этап: исследование архитектуры и подготовка сравнительного PoC.
- Состояние: архитектурное направление и план оценки зафиксированы.
- Реализация: не начата; написание кода требует отдельного согласия пользователя.
- Данные: набор кейса 19 из 26 файлов.

## Цель этапа

Выбрать наиболее точный и проверяемый способ автоматической сверки итогового финансового отчета с первичными документами. На этом этапе необходимо определить компоненты решения, способ измерения качества и критерии перехода к реализации. Целью не является обучение собственной модели.

Результат будущего прототипа должен быть не просто ответом «есть ошибка», а воспроизводимым заключением:

1. какие документы были приняты или исключены;
2. какие значения извлечены из каждого источника;
3. как документы связаны со статьями отчета;
4. по какой формуле получено ожидаемое значение;
5. где в исходном документе находится доказательство;
6. почему система присвоила конкретный статус.

## Исходные ограничения

- Форматы: PDF с текстовым слоем, сканированные PDF, PNG, DOCX и XLSX.
- Язык документов: преимущественно русский.
- Денежные вычисления должны быть точными и воспроизводимыми.
- Недостаток данных нельзя интерпретировать как нулевое значение или финансовую ошибку.
- Неоднозначный результат должен передаваться на ручную проверку.
- Эталонный файл нельзя использовать как вход рабочего контура.
- Конфиденциальные документы нельзя отправлять во внешние API без отдельного разрешения и проверки требований безопасности.

Подробности набора и эталонный результат приведены в [разборе кейса 19](dataset-case-19-audit.md).

## Вывод исследования

Выбран гибридный каскад, а не единая end-to-end модель:

```text
Входные файлы
      ↓
Регистрация, хеширование и определение формата
      ↓
Нативный парсер ───────────────┐
или OCR/VLM для скана          │
      ↓                        │
Каноническая структура данных │
      ↓                        │
Точные фильтры и связи         │
      ↓                        │
LLM-классификация спорных      │
назначений расходов            │
      ↓                        │
Детерминированные вычисления   │
      ↓                        │
Вердикт, reason code и доказательства
```

Такой подход выбран по следующим причинам:

- нативное чтение DOCX и XLSX сохраняет структуру и формулы точнее, чем повторное распознавание визуального представления;
- OCR/VLM необходим только там, где нет надежного текстового или табличного слоя;
- точные признаки должны проверяться раньше нечеткого и семантического сопоставления;
- языковая модель полезна для понимания назначения хозяйственной операции, но не должна выполнять итоговую денежную арифметику;
- каждый вывод должен иметь ссылку на исходную страницу, область, абзац или ячейку.

## Аналоги и применимые практики

### Разбор сложных таблиц

Работа [A Multimodal Data Extraction Pipeline with Table Layout Correction](https://proceedings.mlr.press/v318/yao26a.html) описывает разделение обработки на анализ макета, восстановление структуры таблицы, извлечение по схеме и последующее рассуждение. Для нашего решения это подтверждает необходимость восстанавливать таблицу до финансовой сверки, а не просить одну модель сразу прочитать страницу и посчитать итог.

### Сверка документов

Открытые проекты [InvoiceReconciler](https://github.com/ui-insight/InvoiceReconciler) и [invoice-agent](https://github.com/superintelligenceco/invoice-agent) используют каскад точного и нечеткого сопоставления, отдельную обработку дублей и явные коды причин. Эти проекты рассматриваются как примеры архитектурного паттерна, а не как доказательство production-качества.

### Финансовые рассуждения

Бенчмарки [TAT-QA](https://aclanthology.org/2021.acl-long.254/), [FinQA](https://aclanthology.org/2021.emnlp-main.300/) и [FinMath](https://aclanthology.org/2022.lrec-1.661/) разделяют поиск доказательств и выполнение явных программ вычисления. Из этого следует выбранный принцип: модель определяет релевантные данные, а арифметику выполняет детерминированный расчетный модуль.

### Оценка извлечения из бизнес-документов

[DocILE](https://docile.rossum.ai/) разделяет извлечение ключевой информации и распознавание строк табличных документов. Эта декомпозиция используется в нашей системе метрик: значения полей и структура строк оцениваются отдельно.

## Выбор компонентов

### Нативное извлечение

| Формат | Основной подход | Причина |
|---|---|---|
| XLSX | Чтение листов, ячеек и формул | Сохраняются типы, координаты и выражения |
| DOCX | Чтение таблиц и абзацев | Сохраняется логическая структура документа |
| PDF с текстовым слоем | Текст, блоки и координаты | OCR не вносит дополнительные ошибки |
| Сканированный PDF и PNG | OCR/VLM с распознаванием таблиц | В исходнике нет надежной цифровой структуры |

Если XLSX содержит формулу без сохраненного результата, система должна вычислить поддерживаемое выражение или агрегировать исходные ячейки. Пустое cached value не считается нулем.

### Кандидаты для сканов

| Кандидат | Роль в PoC | Сильная сторона | Ограничение, которое проверяется |
|---|---|---|---|
| [PaddleOCR-VL-1.6](https://github.com/PaddlePaddle/PaddleOCR) | Основной локальный кандидат | Таблицы, структурированный вывод, локальный запуск; PaddleOCR поддерживает русский язык | Точность на русских финансовых формах |
| [MinerU](https://github.com/opendatalab/MinerU) | Локальная альтернатива | Разбор PDF и офисных форматов в структурированный Markdown/JSON | Стабильность таблиц и качество русских реквизитов |
| [Google Document AI Layout Parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk) | Облачный кандидат для разрешенных данных | Макет, таблицы и структурные элементы | Конфиденциальность, стоимость и качество на наборе |
| [Azure Document Intelligence Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0) | Облачная альтернатива | Текст, таблицы, структура и геометрия | Конфиденциальность, стоимость и качество на наборе |

Публичные бенчмарки используются только для формирования короткого списка. Победитель выбирается по нашим документам, поскольку общий результат на benchmark не гарантирует точность на русскоязычной КФЗ.

### Смысловая модель

LLM применяется только к операциям, которые нельзя надежно классифицировать точными правилами. Для текущего набора основная задача — отнесение назначения расхода к статье 0800 или 0900.

Требования к ответу модели:

- строго заданная структура;
- выбранная категория;
- текстовое доказательство из документа;
- ссылка на источник доказательства;
- уровень уверенности;
- возможность вернуть `AMBIGUOUS` или `INSUFFICIENT_DATA`;
- отсутствие самостоятельно вычисленных финансовых итогов.

Стартовый подход — инструкции и несколько размеченных примеров. Тонкая настройка модели на текущем этапе не проводится.

### Детерминированные проверки

Без LLM выполняются:

- SHA-256 и поиск побайтовых дублей;
- нормализация дат, сумм, номеров и договоров;
- проверка отчетного периода;
- проверка принадлежности договору;
- точное сопоставление номера документа;
- агрегирование денежных значений;
- проверка формул и округления;
- вычисление отклонения;
- формирование однозначных кодов причин.

Нечеткое или семантическое сопоставление разрешается только после точных фильтров. Если осталось несколько сопоставимых кандидатов, система возвращает неоднозначность.

## Канонический результат обработки

Для каждого значения необходимы следующие данные:

| Поле | Назначение |
|---|---|
| `raw_value` | Исходное представление в документе |
| `normalized_value` | Нормализованная дата, сумма, номер или категория |
| `document_id` | Устойчивый идентификатор и хеш источника |
| `evidence` | Страница, координаты, ячейка или абзац |
| `extraction_method` | Нативный парсер, OCR или модель |
| `component_version` | Версия примененного компонента |
| `confidence` | Уверенность извлечения, если она определена |
| `review_status` | Автоматически принято, отклонено или требует проверки |

Итоговая сверка должна дополнительно сохранять формулу, входные значения, правило округления и код причины результата.

## Коды причин

Минимальный словарь текущего этапа:

| Код | Значение |
|---|---|
| `OK` | Значение подтверждено |
| `AMOUNT_MISMATCH` | Сумма отчета отличается от ожидаемой |
| `DUPLICATE_DOCUMENT` | Документ уже учтен |
| `OUT_OF_PERIOD` | Документ находится вне отчетного периода |
| `WRONG_CONTRACT` | Документ относится к другому договору |
| `INSUFFICIENT_DATA` | Данных недостаточно для вывода |
| `AMBIGUOUS_MATCH` | Есть несколько допустимых связей |
| `EXTRACTION_ERROR` | Значение не удалось надежно извлечь |
| `UNSUPPORTED_DOCUMENT` | Формат или структура пока не поддерживаются |

## План сравнительного PoC

### Шаг 1. Эталон

На основе ручного разбора фиксируются:

- документ, страница или ячейка каждого значения;
- корректные реквизиты и суммы;
- принадлежность к статье;
- включение или исключение документа;
- итоговая формула и результат;
- ожидаемый код причины.

Эталон хранится отдельно от рабочего входа и используется только после получения ответа системы.

### Шаг 2. Сравнение извлечения

На одинаковом наборе сканов сравниваются как минимум два локальных кандидата. Облачный кандидат добавляется только при разрешенной передаче данных.

Проверяются:

- дата;
- номер документа;
- номер договора;
- сумма;
- валюта;
- назначение операции;
- строки и колонки КФЗ;
- координаты доказательства.

### Шаг 3. Сравнение классификации

Один и тот же нормализованный текст передается выбранной LLM с фиксированными инструкциями и примерами. Отдельно измеряются:

- точность 0800/0900;
- доля необоснованно уверенных ответов;
- полнота доказательств;
- воспроизводимость при повторном запуске.

### Шаг 4. Сквозная проверка

Система должна обработать комплект без доступа к эталонному файлу и воспроизвести известный результат:

- 0200 — 5 558 474,83 руб., без расхождения;
- 0300 — 1 671 359,96 руб., без расхождения;
- 0800 — ожидаемо 1 133 298,10 руб., завышение КФЗ на 12 500,00 руб.;
- 0900 — 3 204 744,51 руб. после исключения невалидных документов;
- общий ожидаемый итог — 11 567 877,40 руб.;
- общий отчетный итог завышен на 12 500,00 руб.;
- документы 09 и 10 распознаны как дубль;
- документ 14 исключен по периоду;
- документ 15 исключен по договору;
- неподтвержденные внутренние подколонки получают `INSUFFICIENT_DATA`.

## Метрики

| Метрика | Что измеряет |
|---|---|
| Exact match реквизитов | Точное совпадение даты, номера, договора и валюты |
| Exact match суммы | Совпадение нормализованного денежного значения |
| Table cell accuracy | Сохранение значения в правильной строке и колонке |
| Classification F1 | Качество отнесения документов к статьям |
| Filter accuracy | Дубли, период и договор |
| Evidence coverage | Доля выводов с корректной ссылкой на источник |
| Final reconciliation accuracy | Совпадение итогового вердикта и размера расхождения |
| False positive rate | Доля корректных строк, ошибочно объявленных проблемными |
| Abstention quality | Корректность статусов неоднозначности и недостатка данных |
| Latency and cost | Время и стоимость обработки комплекта |

Для денежных сумм, договора, периода и итогового расхождения на текущем эталонном комплекте требуется точное совпадение. Если компонент не уверен в результате, безопасным ответом считается ручная проверка, а не угадывание.

## Диверсификация работ

После согласования реализации задачи можно вести параллельно через общие контракты:

| Поток | Результат |
|---|---|
| A. Нативные парсеры | Структурированные данные DOCX, XLSX и текстовых PDF |
| B. OCR/VLM bake-off | Сравнение кандидатов на сканах |
| C. Правила и расчеты | Фильтры, дубли, формулы и reason codes |
| D. Семантическая классификация | 0800/0900, доказательства и отказ от ответа |
| E. Evaluation | Эталон, метрики и независимый сквозной прогон |
| F. Интерфейс доказательств | Связь результата со страницей, областью или ячейкой |

Потоки A–D не должны изменять формат результата независимо друг от друга. Evaluation-поток не использует внутренние подсказки компонентов и оценивает только их зафиксированный выход.

## Решение об обучении моделей

### Сейчас

- Предобучение собственной модели: не требуется.
- Fine-tuning: не требуется.
- Prompting и few-shot-примеры: применяются для смысловой классификации.
- Готовые OCR/VLM: сравниваются на эталонном наборе.

### Когда вернуться к fine-tuning

Дообучение рассматривается только при одновременном выполнении условий:

1. накоплен репрезентативный размеченный набор, существенно больший текущих 26 файлов;
2. ошибки повторяются систематически, а не являются единичными;
3. улучшение парсинга, правил и промпта не устраняет проблему;
4. существует отдельный holdout-набор;
5. определены метрики, стоимость обучения и процедура отката;
6. ожидаемый выигрыш оправдывает поддержку собственной модели.

Пользовательские исправления сначала накапливаются как данные для анализа. Они не запускают автоматическое онлайн-обучение.

## Риски и меры контроля

| Риск | Контроль |
|---|---|
| OCR переставил колонки | Проверка структуры таблицы и координат ячеек |
| LLM придумала значение | Строгая схема, цитата источника и запрет расчетов моделью |
| Дубль учтен повторно | Хеш и составной отпечаток документа |
| Неверная классификация расхода | Few-shot-примеры, доказательство и ручная проверка |
| Пустое значение принято за ноль | Отдельный статус отсутствующего значения |
| Эталон попал во вход | Физическое разделение input и evaluation/oracle |
| Внешний API получил закрытые данные | Локальный режим по умолчанию и отдельное разрешение на облако |
| Высокая точность на одном комплекте не обобщается | Расширение эталона и отдельный holdout до production |

## Результаты этапа

Этап считается завершенным, когда:

- утвержден состав эталонной разметки;
- выбраны кандидаты сравнительного теста;
- согласованы схема данных и коды причин;
- согласованы метрики и критерии приемки;
- определен режим работы с конфиденциальными данными;
- получено отдельное согласие на реализацию PoC.

После этого начинается разработка первого вертикального среза. До такого согласования этот документ является спецификацией исследования, а не разрешением на написание кода.
