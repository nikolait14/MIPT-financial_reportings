# Спринт изоляции браузерской сессии

## Статус

Реализован. Проверены 40 автоматических тестов и сквозной запуск 26 файлов кейса 19:
чужая браузерная сессия получила `404`, а владелец получил ожидаемый
`REPORT_UNRELIABLE` с дельтой 12 500,00 руб. Временные документы после завершения
отсутствуют.

## Цель

Сделать сетевой EPHEMERAL-продукт безопасным для одновременной работы нескольких
пользователей без постоянного хранения их документов. Пользователь загружает комплект,
не перезагружая страницу получает результат и подсветки, а сервер удаляет исходники и
OCR-артефакты после обработки.

Этот спринт не добавляет аккаунты, организации или PERSISTENT-историю. Он устраняет
доступ одной активной браузерской сессии к объектам другой.

## Угроза и граница

Нельзя считать `verification_id` защитой: UUID может попасть в историю браузера,
логи reverse proxy, ссылку, скриншот или быть получен через ошибочный list endpoint.
Любой маршрут, принимающий ID проверки, должен проверить владельца объекта. Это
защищает от класса Broken Object Level Authorization.

Спринт не защищает от пользователя или администратора, имеющего доступ к памяти
сервера, TLS-терминации или диску хоста. Для этого в следующем этапе потребуются
полноценная аутентификация, роли и инфраструктурные меры.

## Контракт сессии

1. При первом `POST /api/v1/verifications` backend создаёт непрозрачный случайный
   session token и возвращает его только как cookie.
2. Cookie имеет флаги `HttpOnly`, `SameSite=Lax`, `Path=/`, ограниченный TTL и флаг
   `Secure` в production.
3. На сервере хранится только SHA-256 токена, связанный с job. Сам token не пишется в
   manifest, результат, логи или error response.
4. Повторные загрузки из той же вкладки используют существующую cookie и получают ту
   же границу доступа.
5. После TTL, закрытия браузера или очистки cookie пользователь теряет доступ к
   session-result; повторная загрузка создаёт новую сессию.

## Правила авторизации

Для `GET /api/v1/verifications` возвращаются только проверки текущей session.

Для каждого маршрута с `{verification_id}` проверяется совпадение hash cookie с
`owner_session_hash` job:

```text
GET    status, events, result, documents, content, evidence, export
POST   rerun
DELETE delete
```

Если cookie отсутствует, не совпадает или объект принадлежит другой session, API
возвращает такой же `404 VERIFICATION_NOT_FOUND`, как для несуществующего ID. Нельзя
раскрывать факт существования чужой проверки через `403` или различающийся ответ.

Stateless endpoints `/api/v1/tools/*` не открывают ранее созданные документы и не
создают историю; в этот спринт они не получают ownership-модель. Для публичного
production им понадобятся rate limiting и полноценная аутентификация.

## Конфигурация

| Переменная | Production default | Назначение |
|---|---:|---|
| `API_SESSION_COOKIE_NAME` | `financial_verification_session` | Имя cookie |
| `API_SESSION_TTL_SECONDS` | `1800` | Время жизни session cookie |
| `API_SESSION_COOKIE_SECURE` | `true` | Передавать cookie только через HTTPS |

Docker Compose предназначен для локальной разработки: порт привязывается к
`127.0.0.1`, а `API_SESSION_COOKIE_SECURE=false` допустим только для локального HTTP.
В опубликованном окружении TLS завершает reverse proxy, cookie возвращается с
`Secure=true`, а backend не публикуется напрямую в интернет.

## Изменения модели данных

В `JobRecord` добавляется `owner_session_hash`. Поле сохраняется только в persistent
manifest как хеш; rerun наследует его от исходной проверки. EPHEMERAL job и результат
остаются в памяти до TTL, а документы очищаются как раньше.

## Приёмка

- первая загрузка устанавливает `HttpOnly`, `SameSite=Lax` cookie;
- session A видит только собственные проверки;
- session B получает `404` на status, result, evidence, export, rerun и delete job A;
- session B не видит job A в list endpoint;
- session A сохраняет прежний happy path и может получить свой отчёт;
- после restart в PERSISTENT доступ имеет только браузер с исходной cookie;
- текущие EPHEMERAL cleanup и case-19 smoke не регрессируют;
- session token и содержимое документов отсутствуют в логах и Git.

## Следующий security-этап

После стабилизации EPHEMERAL UX вместо session capability вводятся OIDC-аутентификация,
`user_id`/`tenant_id`, роли, audit trail, HTTPS-only deployment, проверка MIME/signature
и rate limiting. Тогда эта session-модель станет дополнительным уровнем, а не заменой
полноценного доступа.
