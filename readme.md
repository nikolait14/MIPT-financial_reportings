# Задача 5. Проверка достоверности отчетности по первичным учетным документам

## Текущее состояние реализации

- Реализован локальный PoC распознавания целевой строки КФЗ: 15 из 15 ячеек извлекаются точно в 300, 400 и 600 DPI.
- Реализован Linux/Docker OCR-контур: PaddleOCR 300 DPI выбран основным, Tesseract 400 DPI — независимым full-page fallback; оба варианта дали 15/15 в трех повторах.
- Production OCR не использует эталонные суммы, автоматически переключается на fallback и выдает совместимый со сверкой `report-ocr.json`.
- Реализован `VerificationContext` для договора, периода, отчета и целевой строки.
- Реализован реестр документов с SHA-256, уникальными идентификаторами и доказательствами извлечения.
- DOCX и XLSX обрабатываются нативно; для отчета на Linux используется локальный PaddleOCR/Tesseract, Apple Vision сохранен как macOS-baseline для первичных PDF/PNG.
- Эталонный файл физически исключается из рабочего контура.
- Реализованы `DUPLICATE_DOCUMENT`, `OUT_OF_PERIOD`, `WRONG_CONTRACT`, `EXTRACTION_INCOMPLETE` и изоляция ошибки отдельного файла.
- Реализованы нормализация операций, доказательная классификация в `0200/0300/0800/0900`, точное агрегирование через `Decimal` и сверка с КФЗ.
- Неоднозначная или неизвестная операция не классифицируется принудительно и получает `REVIEW`.
- Для каждого результата сохраняются сумма, формула, исходные документы, фрагменты классификации и координаты или ячейки доказательств.

На наборе кейса 19 получен ожидаемый результат:

- документы 09 и 10 определены как точный дубль;
- документ 14 исключен по периоду;
- документ 15 исключен по договору;
- 19 валидных первичных и расчетных документов классифицированы: 5 в `0200`, 5 в `0300`, 4 в `0800`, 5 в `0900`;
- технических ошибок и документов в `REVIEW` нет.
- статьи `0200`, `0300` и `0900` подтверждены точно до копейки;
- в статье `0800` найдено завышение на 12 500,00 руб.;
- общий подтвержденный итог равен 11 567 877,40 руб. против 11 580 377,40 руб. в КФЗ;
- итоговое заключение — `REPORT_UNRELIABLE`;
- доступная внутренняя детализация зарплаты проверена, а неподтверждаемое разделение помечено `INSUFFICIENT_DATA`.

## Запуск текущего этапа

Linux OCR отчета воспроизводится в Docker и не обращается к внешним API:

```bash
docker compose build report-ocr
docker compose run --rm report-ocr
docker compose run --rm ocr-benchmark
```

Полная текущая сверка использует подготовленный реестр первичных документов и автоматически выбирает Linux OCR отчета, если он создан:

```bash
bash scripts/download_case19.sh
bash scripts/run_case19_registry.sh
bash scripts/run_case19_linux_ocr.sh
bash scripts/run_case19_reconciliation.sh
PYTHONPATH=src python3 -m unittest discover -v tests
```

Подробные результаты и ограничения: [Linux OCR и Docker](docs/financial-report-verification-plan/linux-ocr-docker-results.md).

Результаты создаются в `artifacts/case19-registry/results`:

- `document-registry.json` — полный машиночитаемый реестр с доказательствами;
- `document-registry.csv` — плоский экспорт;
- `document-registry.md` — человекочитаемая таблица.

Результаты сверки создаются в `artifacts/case19-reconciliation`:

- `reconciliation.json` — полный результат с цепочками доказательств;
- `operation-ledger.csv` — нормализованный реестр операций и решений классификатора;
- `reconciliation.md` — человекочитаемое заключение, формулы и источники.

Исходные документы и производные OCR-артефакты не включаются в Git.

## Полное описание

Необходимо разработать систему, которая сопоставляет показатели итогового отчета с первичными учетными документами, на основании которых он был сформирован.

Решение должно находить расхождения в суммах, показателях и других значениях, показывать источник каждого несоответствия и формировать итоговое заключение о достоверности отчета. Пользователь должен иметь возможность понять, из какого документа получено ожидаемое значение и почему конкретная строка отчета считается корректной или ошибочной.

## Вводные данные

На вход подается набор данных, включающий итоговый отчет (КФЗ) и связанные первичные и расчетные документы в разных форматах: PDF, DOCX, XLSX, PNG, в том числе сканы.

Документы различаются по структуре и формулировкам. Связь с показателями отчета определяется по реквизитам (номер договора, период, номер документа) и содержанию. В наборе могут встречаться:

- дубли;
- документы другого периода или договора;
- показатели, для которых подтверждающих данных недостаточно.

В промышленной эксплуатации входные документы могут быть существенно сложнее для извлечения и интерпретации: низкокачественные сканы, нестандартные формы, неполные или ошибочные реквизиты, различная верстка и дополнительные форматы.

## Ожидаемый результат

На вход система получает итоговый отчет и набор связанных первичных документов. На выходе должен формироваться результат сверки, позволяющий проверить каждое найденное расхождение:

1. Статус проверки каждого показателя или строки отчета.
2. Фактическое значение из отчета и ожидаемое значение, рассчитанное или извлеченное из первичных документов.
3. Размер расхождения, если значения не совпадают.
4. Ссылка на первичный документ и конкретный фрагмент, который подтверждает ожидаемое значение.
5. Категория несоответствия, например: расхождение суммы, пропущенный документ, дублирование, неверный период или несовпадение другого показателя.
6. Итоговое заключение о достоверности отчета с краткой сводкой найденных проблем.

## Ограничения

Через любые внешние API можно передавать только открытые (неконфиденциальные) данные.
